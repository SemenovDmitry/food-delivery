# Браузерная приёмка (ZCode in-app browser)

Рецепт накоплен на приёмке этапа 1 (2026-11-15): больше половины браузерных вызовов тогда ушли на переоткрытие этих квирок. Читать **до первой** браузерной приёмки в сессии.

## До старта

- Dev-сервер фоном (`pnpm dev`), БД — контейнер `food-postgres` (dev-компоуз).
- Маршрут после правки кода первый раз открывается долго (dev-компиляция): a11y-снапшоты в это время ловят Suspense-фолбэк. **Поллить готовность элемента** (ненулевой rect, дважды подряд на одной позиции), не верить первому снапшоту.

## Клик и замер

- CSS `scroll-behavior: smooth` держит элементы «нестабильными» для Playwright: `locator.click` часто падает по actionability, `scrollIntoView` не доскролливает. Рабочая пара:
  1. поллинг **стабильного** rect (совпал дважды с паузой),
  2. `window.scrollTo({ top, behavior: 'instant' })` — behavior обязателен, обычный scrollTo асинхронен,
  3. `cua.click` по центру замера; для полей — `locator.fill` (работает надёжнее печати).
- После мягких навигаций `evaluate` изредка читает **устаревший документ** — авторитетная проверка состояния: скриншот (визуал) + БД (`psql`), а не только evaluate.
- `cua.scroll` большими дельтами зависает — дробить по ~300.
- Вкладка «запуталась» (клики не доходят, данные не те) — `browser.tabs.list()`, продолжить в **свежей вкладке**: на новой locator-клики обычно работают.

## Верификация

- Каждый тест-пойнт: скриншот (`emitImage` в том же такте, что и клик — ловить тосты и optimistic-состояния) + опорная точка **вне браузера**: `psql` для БД, `curl` для статусов.
- Негативные кейсы (disabled-кнопки с причиной, модалки ошибок, redirect'ы) — тот же паттерн.
- Консоль браузера недоступна для чтения — видимые проявления ошибки (пустой экран, тост, сломанная раскладка) и есть доказательство; говорить это честно в отчёте.
