# Спека: Этап 2 — Акции (/promo, публичные акции vs скрытые промокоды, API)

Источник правды: AGENTS.md (§6 этап 2, §5.3 кеш, §8). Решение 2026-11-15 (fcf9f22): разделение «публичная акция / скрытый промокод» — `promotions.isPublic`, термины в `GLOSSARY.md` («Публичная акция», «Скрытый промокод»). Гриллинг этапа 2 (2026-11-15/16, Q1–Q9): фильтр публичности — в кешируемом WHERE (безопасность по построению), состав страницы `/promo`, кураторский DTO API, ручной ETag + `s-maxage=60`, приёмка конца окна сдвигом времени.

## Problem Statement

Ссылка «Акции» в шапке и «все →» на главной ведут на несуществующий `/promo` (404). Route Handler'а для акций нет — витрина не имеет внешнего API. Понятия скрытого промокода нет: все акции видны во всех местах (лента, блок корзины), и поле ввода кода на /cart существует «в никуда» — все коды и так видны в списке. Сюжет «код приходит вне приложения (рассылка, реклама)» не демонстрируется. Сценарий «акция исчезает ровно в конце окна» реализован для ленты главной (этап 1), но `/promo` и API ещё не построены на этом механизме.

## Solution

Одна миграция: `promotions.isPublic` (boolean NOT NULL default true — существующие акции остаются публичными). Кешируемая витринная функция фильтрует `isActive + isPublic` прямо в WHERE — лента главной, `/promo`, блок корзины и API получают только публичные по построению; скрытые достаются только поиску по коду (`applyPromoCode`, мимо кеша) и `getPromotionById` (активное промо корзины). Страница `/promo` — кешируемая оболочка + список в Suspense (сетка PromoCard, пустое состояние). `GET /api/promotions` — кураторский DTO + ручной ETag (SHA-256, 304) + `Cache-Control: public, s-maxage=60`. Сидер добавляет скрытый `SECRET15` −15% на весь заказ: в выдачах его нет, применяется только вводом кода на /cart.

## User Stories

1. Как посетитель, я хочу открыть `/promo` (ссылка «Акции» в шапке, «все →» на главной) и увидеть все текущие публичные акции сеткой, чтобы узнать о скидках.
2. Как посетитель, я хочу, чтобы в ленте главной, на `/promo`, в блоке корзины и в API были только публичные акции — скрытые промокоды не утекают никуда по построению, а не по дисциплине каждого потребителя.
3. Как покупатель, я хочу ввести полученный вне приложения код (`SECRET15`) в поле на /cart и получить −15% на весь заказ — единственный путь применения скрытого промокода.
4. Как покупатель, я хочу, чтобы акция исчезла со всех витрин ровно в конце окна — без вмешательства в кеш.
5. Как интегратор (учебный), я хочу `GET /api/promotions` с ETag (304 при неизменных данных) и `Cache-Control: public, s-maxage` — публичные акции доступны внешним потребителям экономно.
6. Как разработчик, я хочу миграцию `isPublic` с default true — существующие акции остаются публичными, а этап 5 получит переключатель в форму акций.
7. Как разработчик (задел этапа 5), я хочу шов: админский список акций — отдельная функция без витринных фильтров (админке нужны и скрытые, и неактивные).

## Implementation Decisions

- **Миграция (drizzle-kit, SQL в git; `db:push` не используем)**: `promotions.isPublic` — boolean NOT NULL DEFAULT true. Сидер пишет `isPublic` явно (`isPublic: promo.isPublic ?? true`) — повторный прогон исправляет дрейф.
- **Сидер SECRET15**: percent 15, `categoryId: null` (весь заказ), `minTotal: 0`, `isPublic: false`, окно как у остальных (startsAt сутки назад, endsAt +30 дней). Код уже в верхнем регистре — `applyPromoCode` нормализует ввод в uppercase.
- **Кеш-фильтр (Q1/Q6 — вариант А)**: `getCachedActivePromotions()` → WHERE `isActive = true AND isPublic = true`. Все 4 витринных потребителя получают только публичные по построению. `getActivePromotions()` без изменений (окно фильтруется на чтении вне кеша, `connection()` первым). Скрытые живут только в `applyPromoCode` (поиск по коду — прямой запрос мимо кеша) и `getPromotionById` (активное промо корзины, без фильтров — ревью C1 не меняется: скрытое применённое промо показывается плашкой). Следствие: в `loadCartViewData` `availablePromos` фильтруется только `code !== null` (безкодовые, Q2 этапа 1) — isPublic доезжает от кеша.
- **Админка — вне скоупа, шов**: витринная кеш-функция не переиспользуется; этап 5 заведёт `getAllPromotions()` без фильтров и обязан звать `updateTag('promos')` в мутациях (общий закон §5.3).
- **Страница `/promo` (Q2 — вариант А)**: `src/app/(shop)/promo/page.tsx` (группа shop — шапка/подвал). Кешируемая оболочка: h1 «Акции» (один h1), `export const metadata`, контейнер `max-w-6xl` (правило 7b26115: новая страница = контейнер). Список в Suspense: `await connection()` первым → `getActivePromotions()`; fallback-скелет. Сетка `PromoCard` как есть (grid-cols-1 sm:2 lg:3, как карточки товаров), без кнопок «Применить» (тизер — применение живёт в корзине). Пустое состояние «Сейчас активных акций нет».
- **API (Q3/Q4)**: `src/app/api/promotions/route.ts`, `GET(request: Request)` — чтение `request.headers` делает роут динамическим (GET-хендлеры с v15 динамические по умолчанию; пререндера с живой БД на docker build нет).
  - DTO: `{ id, name, code, discountType, discountValue, categoryId, minTotal, startsAt, endsAt }`; даты — ISO-строки (`toISOString()`), nullable. Наружу не идут: `isActive` (в выдаче всегда true), `isPublic` (выдача публичная по определению), `createdAt`. Контракт API не повторяет схему БД — при смене схемы (этап 5) DTO не поедет.
  - Данные: `getCachedActivePromotions()` + фильтр окна `isPromoInWindow(p, new Date())` в хендлере (вне кеша).
  - ETag ручной: авто-ETag Next не считается для динамических роутов (`sendRenderResult`: `isDynamic → payload = null`). Strong ETag = `"sha256hex"` от JSON-тела; сравнение с `If-None-Match` точное (наш ETag, учебный проект — без парсинга списков и `W/`).
  - 304: пустое тело + `ETag` + `Cache-Control` (RFC 7232 §4.1). 200: `ETag` + `Cache-Control: public, s-maxage=60` + `Content-Type: application/json; charset=utf-8`. Пустой список → `[]` со своим ETag.
  - `s-maxage=60`: CDN в проекте нет — заголовок демонстративный; окно всё равно точное (Next не кеширует динамический handler). В коде комментарий с доковской оговоркой: CDN не слышит `revalidateTag` и досидит до конца TTL.
  - Скрытые промокоды через API не отдаются (GLOSSARY) — гарантируется кеш-фильтром.
- **Корзина — без изменений**: `applyPromoCode` применяет и публичные, и скрытые коды одинаково (одинаковая ошибка «не найден»); `promoStateReason` не смотрит `isPublic`.
- **Приёмка конца окна (Q5/Q7 — вариант 2, сдвиг времени)**: единственный механизм «исчезновения» — фильтр при чтении (`isPromoInWindow`), таймеров нет; при реальном течении времени акция исчезает ровно в конце окна. Нюанс, вскрытый приёмкой: `'use cache'` хранит снимок строк — прямой SQL-сдвиг `ends_at` невидим чтениям, пока кеш тёплый; фактическая петля проверки — SQL-сдвиг → холодный кеш (рестарт app-контейнера) → мгновенная проверка → откат (детали в тикете 05, грабль §5.29). Полный вариант с реальным ожиданием — примечание в тикете приёмки.

## Готово, когда

3 публичные акции из сидера видны на `/promo` и в API, скрытый `SECRET15` в них НЕ попадает (но применяется вводом кода); акция исчезает ровно в конце окна, без вмешательства в кеш (проверка — сдвигом `ends_at`); lint/tsc/build + docker build + prod compose зелёные; браузерный сценарий web-gui-tester прошёл.

## Вне скоупа

Админ-форма акций с переключателем публичности (этап 5), CRUD акций/категорий, рассылка промокодов (§9), push в origin (по явной просьбе).
