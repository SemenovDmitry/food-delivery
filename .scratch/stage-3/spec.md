# Спека: Этап 3 — Auth (телефон) + привязка email + история заказов

Источник правды: AGENTS.md (§6 этап 3, §5.15 auth-поток, §8). Гриллинг этапа 3 (2026-11-16, Q1–Q5) **изменил план**: регистрация — **только телефон** (чекбокс «email + phone, оба обязательные» отменён), email привязывается отдельным возобновляемым потоком (Q1/Q5); страницы `/login` и `/register` — раздельные (Q2); шапка без имени/телефона — иконка-меню профиля (Q3); промо при слиянии корзин — юзера, иначе гостя (Q4).

## Problem Statement

Ссылка «Войти» в шапке ведёт на несуществующий `/login` (404). Регистрации нет — телефонный auth better-auth (этап 0) не имеет UI: `sendOTP` пишет код в консоль и `notifications`, но форму никто не открывает. Email-верификация (плагин `emailOTP`, `sendEmail` → Mailpit) стоит без потребителя. Гостевая корзина (`cart_id`-cookie) при входе не доезжает до аккаунта — `carts.userId` не проставляется. `/orders` закрыт: есть только квитанция по uuid-ссылке, своей истории пользователь не видит.

## Solution

Две страницы-близнеца `(auth)/login` и `(auth)/register` (визард «телефон → SMS-код» с разным гардом), поток привязки email `(auth)/email` (email → код из Mailpit → `emailVerified`), dropdown-меню профиля в шапке (иконка, без имени), страница `/orders` (гард по сессии: текущий заказ + история + баннер привязки email). Слияние гостевой корзины — server action после успешного verify. Миграций БД нет — схема готова с этапа 0.

## Механика better-auth (проверено по исходникам node_modules, определяет решения)

1. **Пользователь создаётся только в момент ввода кода** (`verifyPhoneNumber`): юзер не найден + `signUpOnVerification` → create, причём доп-поля из body распаковываются, но **`email` перетирается `getTempEmail` (`phone-<digits>@temp.food.local`) и `name` — `getTempName` (телефон)**. Настоящие email/имя нельзя передать «попутно» — только отдельным серверным шагом после verify (или никогда — решение Q1/Q5: имя не собираем вовсе, email — в потоке привязки).
2. **`sendOTP` не проверяет существование номера** — шлёт код кому угодно. Проверки «зарегистрирован / не зарегистрирован» — наши server actions ДО вызова `auth.api.sendPhoneNumberOTP` (точка ошибки «зарегистрируйтесь», §5.15; и обратная — register отклоняет занятый телефон).
3. **`sendVerificationOtp` (email) молча не шлёт письмо для несуществующего email** (анти-энумерация). Порядок потока привязки строго: action кладёт email на юзера (явная проверка уникальности — `changeEmail` при дубликате молчит, что для формы плохо, Q1-вариант C отклонён) → потом запрос кода.
4. **Парольного входа нет**: `signInPhoneNumber` требует password — не используем. Вход = тот же тандем send-otp → verify (для существующего юзера verify проставляет `phoneVerified` и создаёт сессию).
5. **Rate limits (prod)**: `/phone-number/*` 10/мин, `/email-otp/send-verification-otp` 3/мин — для демо достаточно, не трогаем.
6. **Телефон — точное совпадение строк** (сидер: `+7 999 000-00-01`): нормализация ввода обязательна, иначе вход демо-аккаунтов ломается на формате.

## User Stories

1. Как новый клиент, я хочу зарегистрироваться по телефону за два шага (номер → SMS-код), чтобы сразу получить аккаунт и оформить заказ.
2. Как клиент, я хочу войти по телефону демо-кодом 1111 (в любом разумном формате ввода: `8…`, без пробелов, с пробелами), чтобы попасть в свою историю заказов.
3. Как клиент, я хочу привязать email позже (ввёл адрес → код из письма в Mailpit → «верифицирован»), чтобы сделать это когда удобно — закрыл браузер, вернулся, CTA всё ещё ведёт на недоделанный шаг.
4. Как клиент, я хочу видеть свои заказы на `/orders` (текущий отдельно от истории), чтобы отслеживать и пересматривать их без uuid-ссылки.
5. Как клиент, я хочу, чтобы гостевая корзина при входе доехала до аккаунта (товары просуммировались, промо сохранилось), чтобы не собирать заказ заново.
6. Как клиент с незарегистрированным номером, я хочу на `/login` ясную ошибку «зарегистрируйтесь» со ссылкой — а не молчаливое создание аккаунта (§5.15).

## Implementation Decisions

- **Q1/Q5 — регистрация только телефон, email отдельно**: verify создаёт юзера с temp-email → сразу редирект; ничего на temp-email не делаем. Поток привязки: `linkEmail` action (сессия; не уже-ли верифицирован; уникальность email с явной ошибкой; UPDATE user; `auth.api.sendVerificationOTP(type: 'email-verification')` → Mailpit) → ввод 6-значного кода → `authClient.emailOtp.verifyEmail` → `emailVerified`. Поток возобновляемый: страница `/email` доступна пока `!emailVerified`; повторный вход в неё шлёт новый код. Причины: одна лишняя форма + шаг в регистрации тяжёлее первый вход; email-механизм демо выигрывает (возобновляемый, повторяемый); temp-email на аккаунте безвреден — `user.email` пока ничто не потребляет (рассылки — §9). Согласовано изменение плана — зафиксировано здесь и будет в AGENTS при закрытии этапа.
- **Q2 — две страницы**: `(auth)/login` и `(auth)/register`, кросс-ссылки; `(auth)/layout.tsx` — минимальный центрированный каркас без шапки магазина, `<main id='main-content'>`, ссылка «← в меню». Общий клиентский компонент визарда (`mode: 'login' | 'register'`): шаг «телефон» → `sendLoginOtp`/`sendRegisterOtp` → шаг «код 1111» → `authClient.phoneNumber.verify` → слияние корзины → `router.push(redirect)`. Тексты и гарды разные: login незнакомый телефон → «Номер не зарегистрирован — зарегистрируйтесь» (ссылка), register занятый → «Этот номер уже зарегистрирован — войдите» (ссылка). Гард страниц: сессия + `emailVerified` → redirect (login → `?redirect || '/orders'`; register → `/orders`); `/email` без сессии → `/login`.
- **Q3 — шапка без имени**: авторизован — иконка-кнопка `UserRound` (aria-label «Профиль») → DropdownMenu: «Мои заказы» (`/orders`), «Привязать email» (`/email`, только пока `!emailVerified`), разделитель, «Выйти». Гость — «Войти» → `/login` (как есть).
- **Q4 — слияние корзин** (`mergeGuestCartOnAuth`, явный action, вызывается клиентом после успешного verify в обоих потоках): нет cookie-корзины — no-op; у юзера нет корзины — усыновление гостевой (`userId` на неё); обе есть — транзакция: qty суммируются с капом `MAX_QTY`, промо `userCart.promoId ?? guestCart.promoId`, гостевая корзина удаляется, cookie снимается; `revalidatePath('/')`.
- **Телефонная нормализация** (`lib/phone.ts`, чистая функция): `8…`/`7…`/10 цифр → канон `+7 XXX XXX-XX-XX` (точно формат сидера); иначе null → zod-refine «Введите номер в формате +7 999 000-00-01». RU-only — демо.
- **Формы = RHF + zod** (`lib/schemas/auth.ts`: `phoneSchema` с нормализацией, `otpCodeSchema` (4), `emailOtpSchema` (6), `linkEmailSchema` (email); тип = `z.infer`, клиент zodResolver, сервер парсит те же схемы) — конвенция CheckoutForm.
- **Redirect**: `?redirect=`-параметр (валидация: только локальные пути, начинающиеся с `/`), дефолт `/orders`.
- **`/orders`** (`(shop)/orders/page.tsx`, гард: `getSession()` → null → `redirect('/login')`): Suspense-обёртка (паттерн квитанции), `getUserOrders(userId)` — текущий = последний с статусом в `created|preparing|ready|in_delivery`, история = остальные (терминальные), desc. Карточка: № (uuid slice 8), дата, статус-бейдж (STATUS_LABELS), N позиций, итог (Σ позиций − скидка + доставка — формула квитанции), ссылка на квитанцию/трекинг. Без `'use cache'` (персональные данные). Баннер «Привязать email» пока `!emailVerified`.
- **Приёмка**: dev — Mailpit :8025; вход/регистрация демо-аккаунтов; merge корзины; гард `/orders` гостя; БД-верификация (user: temp-email до привязки, real после, флаги; carts.userId; notifications `otp.auth`).

## Готово, когда

Регистрация нового клиента проходит по телефону + SMS 1111 (консоль + строка в `notifications`), аккаунт создан с `phoneVerified` и temp-email; привязка email проходит через случайный код из Mailpit (без `SMTP_HOST` — консоль) → `emailVerified`; вход демо-аккаунтами по телефону работает в форматах `89990000001` / `+7 999 000-00-01`; вход по незарегистрированному телефону — «зарегистрируйтесь»; история на `/orders` видна только владельцу (гость → redirect `/login`); гостевая корзина доехала до аккаунта (qty просуммированы, промо юзера иначе гостя); lint/tsc/build + docker build + prod compose зелёные; браузерный сценарий web-gui-tester прошёл (рецепт §5.25); AGENTS обновлён (чекбоксы + §3 + решение «регистрация только телефон»), коммит.

## Вне скоупа

Смена/перепривязка уже верифицированного email; пароли и `signInPhoneNumber`; OAuth; правки rate limits; имя пользователя в UI (user.name остаётся телефоном/временным); email-рассылки о заказах (этап 10); админка пользователей (этап 5); push в origin (по явной просьбе).
