# Этап 10 — Уведомления (аутбокс) + автоджоба статусов. Спека

Дата: 2026-11-17. Контекст: этап 9 (оплата) принят против prod-стека; этап 10 — вторая из трёх финальных фич. Заделы этапа 0 уже в коде: таблица `notifications` аутбокс-готова (`channel` email|sms, `event` order.ready|otp.auth, `payload` jsonb, `status` default `pending`, `error`), `order_status_events`, env `DEMO_AUTO_STATUS`/`DEMO_AUTO_STATUS_INTERVAL`. Задел этапа 9: статус `cancelled_by_timeout` пишется только ленивыми TTL-гардами (`webhook-core`, pay-страница, админка) — «свип — в автоджобу этапа 10».

Гриллинг Q1–Q11 проведён 2026-11-17, все решения подтверждены пользователем (ниже — канонический фикс). Терминология — GLOSSARY («Аутбокс», «Флушер», «Свип», «Автоджоба»).

**Миграций нет.** `notifications` уже имеет `status`/`error`; OTP-строки пишутся сразу со `status: 'sent'` (интерактивный путь, §5.16) — флушер их не трогает, берёт только `pending`.

## Решения гриллинга

| Q   | Решение                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Q1  | Фоновые процессы живут в **`src/instrumentation.ts`** (`register()` — по докам Next 16 вызывается один раз при старте сервер-инстанса, dev и standalone-prod): старт флушера (30 с) и тика джобы (`DEMO_AUTO_STATUS_INTERVAL`, кламп ≥ 5 с). Гварды: `globalThis`-синглтон от дублей при HMR; `NEXT_PHASE === 'phase-production-build'` на случай вызова при сборке (проверить эмпирически на docker build — §5.3, живая БД при сборке недоступна). Compose не меняется                                                                                                                                      |
| Q2  | **Свип — всегда** (dev и prod), это корректность, а не демо; продвижение статусов — под `DEMO_AUTO_STATUS=true`. Без свипа неоплаченный онлайн-заказ, по которому клиент не вернулся, в проде висит вечно (ленивые гарды срабатывают только на взаимодействии). Каденс свипа = тик джобы (60 с → просрочка висит ≤ 1 мин после конца окна). Ленивые TTL-гарды остаются (defense in depth)                                                                                                                                                                                                                    |
| Q3  | **Общее ядро `transitionOrderStatus(orderId, next)`** в lib (без auth, без кеш-вызовов): карта `nextStatuses`, гвард платной отмены, гвард кухни, `collectOnReceipt`, conditional UPDATE, строка в `order_status_events`, **SMS-строка при `ready` в той же транзакции**. Action-обёртка `updateOrderStatus` = `requireAdmin` + `isUuid` + `updateTag('orders')` + `revalidatePath('/admin/orders')`; джоба-обёртка = выборка кандидатов + решения. «Любая смена статуса пишет событие» — по построению; SMS рождается и от ручного перехода админа, и от джобы. Тексты ошибок action'а сохраняются дословно |
| Q4  | **По-заказный elapsed**: тик берёт активные заказы с `updatedAt <= now - interval`, двигает каждый ровно на один шаг (`nextStatuses(status, fulfillment)[0]`). Заказ, созданный секунду назад, не прыгает — у каждого свой ритм от последней смены статуса. Неоплаченные онлайн не продвигаются вовсе (гвард кухни; судьбу решает свип по окну)                                                                                                                                                                                                                                                              |
| Q5  | Рол vendor-отмены: **одиночный, в точке `created→preparing`**, только для `on_receipt` (неоплаченные онлайн — епархия свипа, оплаченные гвардят себя), с вероятностью `DEMO_AUTO_CANCEL_RATE` (дефолт 0.1). ≈10% заказов (а не 19% при роле на каждом из двух шагов). Ручные переходы админа рол не проходят — хаос только у джобы. Ставка в env → приёмка ставит 0/1 для детерминизма                                                                                                                                                                                                                       |
| Q6  | SMS «заказ готов»: получатель = `orders.phone` (гости тоже — телефон есть у каждого заказа); текст рендерится **в момент вставки** (флушер ничего не знает о заказах): доставка — «Ваш заказ № XXXXXXXX готов — курьер скоро выедет», самовывоз — «…готов к самовывозу», номер — короткий id `slice(0, 8)` как в UI. Строка: `channel='sms'`, `event='order.ready'`, `status='pending'`, payload `{to, text, orderId, fulfillment}`. Каждый заказ проходит `ready` ровно один раз → ровно одна строка на заказ                                                                                               |
| Q7  | Провайдеры — seam для roadmap-замены: `SmsProvider` (консоль-заглушка по образцу `sendOTP`) + `EmailProvider` (обертка существующего `sendEmail` → Mailpit, без `SMTP_HOST` — консоль). Флушер: тик 30 с, `SELECT pending ORDER BY createdAt LIMIT 20`, по строке — провайдер по `channel` → `UPDATE sent                                                                                                                                                                                                                                                                                                    | failed` (+`error`); **failed — терминален, без ретраев** (SMTP-сбой не должен лупить бесконечно); неизвестный канал → failed «Нет провайдера для канала». EmailProvider продюсеров в этом этапе не имеет — приёмится подсаживанием `pending`-строки SQL'ем; UI аутбокса нет |
| Q8  | Свип зеркалит предикат TTL-гарда webhook-core (`online && paymentStatus=pending && status IN ACTIVE_STATUSES && createdAt + window < now`), идёт **по-заказными транзакциями** (conditional UPDATE заказа → `cancelled_by_timeout`, payment → `cancelled`, событие — шейп ветки expired); сбой одного заказа не роняет партию. Внутри тика свип выполняется **до** продвижения. Reentrancy-флаг: тик, застрявший дольше интервала, пропускается, не наслаивается                                                                                                                                             |
| Q9  | Приёмка — **гибрид**: prod-стек принимается ровно как будет жить (полный цикл сборки, свип неоплаченного, флушер: админ → `ready` → pending → SMS в консоль ≤ 30 с → `sent`, EmailProvider подсадной строкой), автоджоба — в dev (`DEMO_AUTO_STATUS=true`, интервал 5000, ставка 0 → вся цепочка до терминала без админки; ставка 1 → детерминированная vendor-отмена; онлайн-оплаченный едет после оплаты). Prod не фальшивится временно-правками compose                                                                                                                                                   |
| Q10 | `DEMO_AUTO_STATUS=true` в `.env.example` и локальном `.env` (по плану «dev on, prod off»; prod-compose флаг не задаёт → prod off). Шум живых заказов при dev-разработке принят — флаг локально выключаем на время отладки                                                                                                                                                                                                                                                                                                                                                                                    |
| Q11 | Граница: в этом этапе рождается **только** `order.ready` SMS. Нет SMS при отменах (видно на трекинге), нет «курьер в пути» на `in_delivery`, нет email-дублей «заказ готов», `promo.blast` — роадмап. Новый тип уведомления = новый продюсер над тем же аутбоксом, без переделки шва                                                                                                                                                                                                                                                                                                                         |

## Архитектура

```
src/instrumentation.ts — register(): один раз на процесс сервера (dev + standalone prod)
 ├─ globalThis-гвард (HMR-дубли), гвард NEXT_PHASE=phase-production-build (docker build)
 ├─ startFlusher()  lib/notifications/flusher.ts   setInterval 30 с
 │    pending (LIMIT 20, ORDER BY createdAt) → provider(channel) → sent | failed(+error)
 └─ startAutoStatusJob()  lib/jobs/auto-status.ts  setInterval max(INTERVAL, 5с), reentrancy-флаг
      1) свип (всегда): просроченные online+pending → cancelled_by_timeout (по-заказные tx)
      2) продвижение (DEMO_AUTO_STATUS=true): elapsed-кандидаты → один шаг через ядро

updateOrderStatus (action: requireAdmin + updateTag + revalidatePath) ─┐
                                                                       ├─▶ transitionOrderStatus
автоджоба (выборка + решения: elapsed, рол, свип) ─────────────────────┘   [lib, без auth/кеша]
      карта nextStatuses → гварды оплаты → conditional UPDATE → event → SMS@ready (одна tx)
```

- `lib/order-transition.ts` — ядро перехода (выносится из `updateOrderStatus` без изменения поведения; тексты ошибок — дословно: «Заказ не найден», «Недопустимый переход статуса», «Оплаченный заказ отменить нельзя», «Заказ ожидает оплаты», «Статус уже изменён — обновите список»).
- `lib/notifications/` — `providers.ts` (интерфейсы + консольный SMS + email-обертка `sendEmail`), `flusher.ts` (экспортирует `flushOnce()` — для смоука через tsx — и `startFlusher()` — для instrumentation), рендер текста `order.ready`.
- `lib/jobs/auto-status.ts` — `autoStatusTick()` (`flushOnce`-паттерн: экспорт для смоука) + `startAutoStatusJob()`; чтение env по образцу `window.ts` (zod-env — этап 11).
- Заказы читаются без `'use cache'` (персональные данные) → джоба не обязана звать `updateTag`; кеш-вызовы остаются в action-обёртке (джоба вне request-контекста).
- ws-gateway не затрагивается (уведомления — домен Next-приложения).

## Поток (канонический)

1. **Заказ создаётся** (`created`, on_receipt или неоплаченный online) → джоба (dev) или админ двигает его.
2. **Свип** (каждый тик, всегда): `online + pending + истекло окно` → `cancelled_by_timeout` + payment `cancelled` + событие. Ленивые гарды остаются как страховка.
3. **Продвижение** (dev, флаг включён): заказ с `updatedAt` старше интервала → следующий шаг карты `nextStatuses`. В точке `created→preparing` on_receipt-заказ с вероятностью `DEMO_AUTO_CANCEL_RATE` уходит в `cancelled_by_vendor`.
4. **`ready`** — ядро в той же транзакции пишет SMS-строку аутбокса (`order.ready`, `pending`).
5. **Флушер** (30 с): строка → SMS-провайдер (консоль-заглушка; настоящий провайдер = новый файл + env) → `sent`. Оплаченные никогда не отменяются (гвард платной отмены в ядре; свип смотрит только `pending`).
6. **Терминал**: доставка `delivered` (on_receipt → `paid` той же транзакцией), самовывоз `picked_up` — джоба доходит до терминала и заказывается из выборки.

## Данные и миграции

- **Миграций нет** — все структуры готовы (`notifications.status/error`, `order_status_events`, `cancelled_by_timeout` этапа 9).
- Env: `.env.example` — `DEMO_AUTO_STATUS=false → true` (+коммент «dev on / prod off: prod-compose не задаёт»), `DEMO_AUTO_STATUS_INTERVAL` — коммент «тик автоджобы, мс (кламп ≥ 5000)», новый `DEMO_AUTO_CANCEL_RATE=0.1`; локальный `.env` — `DEMO_AUTO_STATUS=true`. Prod-compose флаги не задаёт (prod off по умолчанию).

## Границы скоупа

- Только `order.ready` SMS; отмены/`in_delivery`/email-дубли — не в этапе (Q11).
- failed — терминален, ретраев нет (Q7).
- UI аутбокса нет — строки видны в БД, консоли приложения и Mailpit.
- pino/структурные логи и zod-env — этап 11; сейчас `console.log` и паттерн `window.ts`.
