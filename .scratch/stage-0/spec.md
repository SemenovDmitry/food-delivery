# Спека: Этап 0 — базовая кодовая база (вариант Б, пересборка с нуля)

Источник правды: AGENTS.md (§2 стек, §5 грабли, §6 этап 0, §11 детальная спецификация). Решения гриллингов 2026-11-15: prod-заглушки (телефонный auth, Mailpit, 8 статусов, таблицы-заделы), раскладка главной (hero + «Акции недели» + меню, якорная навигация со scrollspy, «Популярное» — отложено). Термины — `GLOSSARY.md`.

## Problem Statement

Проект Food Delivery существует только как план: в репозитории нет кода. Нужна базовая кодовая база, которая с первого дня ведёт себя как «production ready на бесплатных заглушках»: работающий каркас магазина с меню на главной, вся инфраструктура в Docker, схема БД с заделом под будущие этапы (оплата, уведомления, мониторинг ошибок), auth-инфраструктура better-auth и кеширование Cache Components — без отдельного бэкенда и без платных сервисов.

## Solution

Пересборка с нуля: create-next-app (Next.js 16, TS strict, Tailwind v4, `src/`, pnpm 11), PostgreSQL 17 + Drizzle (pg-core, postgres-js) в docker-compose, multi-stage Dockerfile со standalone-сборкой. Каркас магазина: header/footer, главная `/` = меню («Акции недели» в Suspense + sticky-навигация по категориям с якорным скроллом и scrollspy + поиск), карточки товаров с emoji-фолбэком, модалка товара через intercepting route и fallback-страница. Схема БД сразу содержит 8 статусов заказа и пустые таблицы-заделы payments/notifications/error_events. better-auth с phone-number plugin (SMS-OTP — фейк-код 1111), идемпотентный сидер (5 категорий, 24 товара, 4 акции, 3 демо-аккаунта с телефонами и верифицированными email). Server actions корзины и заказа, queries с кеш-тегами `menu`/`promos`.

## Implementation Decisions

- Монолит Next.js без отдельного бэкенда: чтения — RSC напрямую из БД, записи — Server Actions; Route Handlers в проекте всего 6 (auth, orders/[id], promotions, chat, payments webhook, health) — на этапе 0 фактически создаётся только auth-handler, остальные появляются в своих этапах.
- next.config: `cacheComponents`, `partialPrefetching`, `reactCompiler` (+ dev-dep babel-plugin-react-compiler), `output: 'standalone'`.
- Кеш: `getFullMenu` — `'use cache'` + `cacheLife('hours')` + тег `menu`; `getActivePromotions` — кешируются данные (isActive=true), окно дат фильтруется на чтении вне кеша, тег `promos`; корзина/заказы — без кеша. Главная — кешируемая оболочка + Suspense-блоки (акции, меню). Точные TTL профилей `cacheLife` сверяются с `node_modules/next/dist/docs` (чекбокс этапа).
- Главная: «Акции недели» — Suspense над меню (hero-блок удалён по решению пользователя 2026-11-15); меню сгруппировано по категориям в порядке Пицца → Шаурма → Сеты → Напитки → Десерты. «Популярное» — отложено до появления заказов (§9).
- Навигация меню: sticky-пилюли под header — нативные якорные ссылки (`#pizza` и т.п.), секции с `scroll-margin-top` под высоту sticky-блока, плавный скролл через CSS с уважением `prefers-reduced-motion`, scrollspy — клиентский компонент на IntersectionObserver. Поиск — нативная GET-форма с `?q` (searchParams читаются в Suspense-скоупе). Фильтр `?category` удалён из схемы — deep-link даёт сам хэш.
- Модалка товара: intercepting route (`@modal`) перехватывает ссылку `/product/[id]` с главной; product-details имеет два режима (asDialog через router.back() / страница); fallback-страница с `generateMetadata`.
- Корзина: серверная (`carts`/`cart_items`), гостю — httpOnly-cookie `cart_id`; actions add/setQty/remove + `createOrder` + `applyPromoCode` — состав и цены из БД, снапшот, промокод ревалидируется на сервере, запись в `db.transaction()`, результат `ActionResult`. UI корзины — этап 1.
- Схема: статусы заказа — фиксированное множество из 8 (`created`, `preparing`, `ready`, `in_delivery`, `delivered`, `picked_up`, `cancelled_by_customer`, `cancelled_by_vendor`); `orders.paymentStatus` pending|paid; таблицы `payments` (order_id, amount в копейках, status created|processing|paid|failed|cancelled, provider, external_id), `notifications` (channel, event, payload, status pending|sent|failed, error), `error_events` (level, message, stack, context) — пустые, под этапы 9–11; user — phone (уникальный) + email (обязательный) + флаги верификации; деньги — int копейки.
- Auth: better-auth + drizzleAdapter + phone-number plugin; `sendOTP` — фейк-код `DEMO_SMS_OTP_CODE` (по умолчанию `1111`): console.log + строка в `notifications`; email-верификация — случайный код письмом (SMTP → Mailpit в dev, без `SMTP_HOST` — код в консоль); роли — additionalField admin/manager/customer с `input: false`; cookieCache 5 мин. UI вкладок входа — этап 3.
- Сидер идемпотентный: 5 категорий, 24 товара (8 пицц, 6 шаурм, 3 сета со `set_items`, 4 напитка, 3 десерта), 4 акции (`SHAWARMA20` −20%, `COMBO150` −150₽, `PIZZA300` −300₽, «Счастливые часы» без кода с окном дат), 3 аккаунта (`+7 999 000-00-01/02/03` — admin/manager/customer, email admin/manager/client@food.local, оба флага верификации true).
- Шрифты: Geist latin+cyrillic → переменная `--font-sans` (требование пресета nova). Темы: next-themes (attribute=class, system), переключатель без mounted-состояния (обе иконки рендерятся, видимость через `dark:` классы).
- ESLint: jsx-a11y только правилами из `flatConfigs.recommended.rules` (плагин уже зарегистрирован eslint-config-next).
- pnpm 11; `allowBuilds: esbuild` в pnpm-workspace.yaml.

## Testing Decisions

- Тестовый фреймворк отсутствует (vitest/Playwright — §9, осознанно). Единственный шов — самый верхний: запущенное приложение целиком. Новых швов не заводим.
- Хороший тест здесь = проверка внешнего поведения: статус HTTP, наличие секций в разметке, записи в БД — не внутренности реализации.
- Проверки этапа (совпадают с чекбоксом «Проверка» в AGENTS.md): `GET /` → 200 с секциями акции/меню; `?q` фильтрует секции; `/product/[id]` → 200; схема после миграций содержит все таблицы и 8 статусов; повторный `db:seed` не создаёт дублей; вход по телефону с OTP `1111` через auth-endpoints; `pnpm lint` чист; `docker build` проходит; `docker compose up` поднимает postgres+minio+mailpit и приложение отвечает.
- Инструменты прогона: curl, psql, docker CLI, ручной браузерный проход.
