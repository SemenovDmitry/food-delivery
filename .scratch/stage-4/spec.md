# Спека: Этап 4 — Трекинг заказа

Источник правды: AGENTS.md (§6 этап 4, §5.14 ETag, §5.24 uuid-гард, §8). Гриллинг этапа 4 (2026-11-16, Q1–Q15) **переопределил план**: таймлайн — клиентский `OrderTracker` с поллингом **25 с** через ETag (Q1/Q6); доступ — «uuid открывает статус, сессия открывает чувствительное» (Q11a, заменила «владелец по сессии или uuid» из старого плана); отмена клиентом добавлена в этап (Q2/Q12 — раньше вообще не была запланирована ни на одном этапе); карточка **всех** активных заказов на главной до акций (Q10); таблица `order_status_events` создана в этапе 4 с писателями по ходу этапов (Q13/Q15a).

## Problem Statement

Квитанция `/orders/[id]` (этап 1) показывает статус-бейдж «Создан» и никогда не меняется — заказа «оживающего» без перезагрузки нет; `GET /api/orders/[id]` не существует (в §5.14 про него написано, роута нет). Статус `cancelled_by_customer` — «висячий»: есть в енуме и `STATUS_LABELS`, но ни один action его не ставит. У залогиненного пользователя на главной нет признака живого заказа — надо идти в `/orders`. История смен статусов нигде не копится — в этапе 10 таймлайну с временами шагов будет не откуда взяться.

## Solution

Трекинг поверх квитанции: чистая функция таймлайна + клиентский `OrderTracker` (поллинг 25 с, ETag → 304 экономит тело), Route Handler `GET /api/orders/[id]` с минимальным DTO и ручным ETag (паттерн `GET /api/promotions`), маскирование адреса/комментария по сессии, отмена клиента с Dialog-подтверждением, карточка активных заказов на главной, миграция `order_status_events` с писателями `createOrder`/`cancelOrder`.

## User Stories

1. Как гость, я хочу открыть ссылку отслеживания и видеть таймлайн статуса, который обновляется сам (≤25 с, без перезагрузки), чтобы не жать F5.
2. Как владелец по сессии, я хочу видеть на той же странице ещё и адрес/комментарий — а держатель ссылки нет (чувствительное — только своё).
3. Как клиент, я хочу отменить заказ, пока он не готов, с подтверждением — и сразу видеть баннер отмены.
4. Как залогиненный клиент, я хочу видеть на главной свои активные заказы со статусами (все, не один), чтобы одним взглядом понять, что происходит, и кликом попасть в трекинг.
5. Как клиент, я хочу, чтобы после завершения заказа (доставлен/выдан/отменён) страница успокаивалась — поллинг замолкает.

## Implementation Decisions (гриллинг Q1–Q15, 2026-11-16)

- **Q1 — архитектура**: RSC рендерит страницу, начальный статус — проп клиентского `OrderTracker`; поллинг `fetch` + `If-None-Match` → 304 ничего / 200 `setState`. Шаги строит чистая `buildTimeline(status, fulfillment)` в `lib/order-timeline.ts` (паттерн `cart-totals` — одинаково для RSC и клиента). `router.refresh()`-альтернатива отклонена: полный re-render RSC без выгоды ETag.
- **Q2 — таймлайн**: ветка по fulfillment (доставка: `created→preparing→ready→in_delivery→delivered`; самовывоз: `…→ready→picked_up`); шаги — иконка (lucide) + текст, done/current/pending; отмены — destructive-баннер ВМЕСТО таймлайна («Вы отменили этот заказ» / «Заказ отклонён заведением»).
- **Q3/Q13 — времена шагов**: без пошаговых времён в UI этапа — подпись «Статус обновлён …» из `updatedAt`. Таблицу событий создать сейчас, времена на шагах — этап 10.
- **Q15a — `order_status_events`** (order_id FK cascade, status, created_at): миграция в этапе 4; писатели подключаются по ходу этапов — `createOrder` пишет `created` (в существующей транзакции), `cancelOrder` пишет отмену, этап 5 (`updateOrderStatus`) и этап 10 (автоджоба) — чекбоксы уже в AGENTS; с момента появления таблицы нет ни одного писателя статуса мимо неё. UI таблицу пока не читает; заказы, созданные до этапа 4, без истории — фолбэк «без времени» в этапе 10.
- **Q4/Q14 — API**: DTO `{status, paymentStatus, updatedAt}` (ISO) — минимум для обновления таймлайна; состав/итоги снапшотные и уже отрендерены. `fulfillment` в DTO не нужен — неизменен, идёт пропом из RSC. `paymentStatus` включён заранее (этап 9 перевернёт webhook'ом — контракт не меняется). ETag = sha256 тела, точное сравнение `If-None-Match`, 304 повторяет ETag+Cache-Control (паттерн `GET /api/promotions`, этап 2).
- **Q5 — ошибки и кеш API**: не-uuid (гард `isUuid` до БД, §5.24) и не-найден → 404; трекер на 404 молча останавливает поллинг (страница уже отрендерена). `Cache-Control: private, no-store` — персональные данные (в отличие от акций: там `public, s-maxage=60`); ETag-флоу от no-store не ломается.
- **Q6 — поллинг 25 с**: в тике `document.hidden` → skip; ошибки сети — молча, без бэккофа и UI-ошибки; терминальный статус (`delivered|picked_up|cancelled_*`) → `clearInterval`; смена статуса объявляется `aria-live="polite"`.
- **Q7/Q11a — доступ**: uuid = пропуск (как у страницы с этапа 1) — API тоже проверяет только существование uuid, сессию не смотрит (DTO без личных полей). На странице: `isOwner = session.user.id === order.userId` → адрес/комментарий только владельцу; держатель ссылки — таймлайн+состав+сумма; гостевые заказы (`userId=null`) скрыты для всех. «Скопировать ссылку» — у всех. Готово-когда про гостя по ссылке сохранено. Строгий guard (только владелец) отклонён: гостевые заказы стали бы неотслеживаемыми в принципе.
- **Q12 — отмена клиентом**: кнопка только при `created|preparing` (иначе не рендерится), гард `paymentStatus=pending` (задел этапа 9: оплаченные = refund, вне скоупа), action повторно проверяет статус в транзакции (гонка: `WHERE id AND status IN ('created','preparing') AND payment_status='pending'` → 0 строк = error «Заказ уже в работе — отменить нельзя» → toast), Dialog-подтверждение, успех → мгновенный `setState('cancelled_by_customer')` (баннер сразу; следующий тик подтвердит тот же ETag) + строка в events. Отменяет тот, кто видит страницу (владелец или держатель ссылки).
- **Q10 — карточка активных заказов на главной**: Suspense-слот НАД «Акциями недели» (чтение сессии — динамическое, §5.3; гость слота не видит вовсе); **все** активные (`created|preparing|ready|in_delivery` — те же `ACTIVE_STATUSES`, что на /orders): № (slice 8), бейдж статуса, Σшт + сумма, вся карточка — ссылка → `/orders/[id]`; без поллинга (живое обновление — на трекинге); пусто → слот не рендерит ничего.
- **Q8 — вне скоупа**: платёжный бейдж UI (этап 9; поле в DTO уже есть), ETA (поля нет в схеме), отмена оплаченных (refund — §9), кнопка отмены заведением (этап 5).
- **Q9 — приёмка**: статусы двигаем прямым SQL — легально именно здесь: роут динамический (чтение request), заказы без `'use cache'` → §5.29 не применяется, свежесть мгновенная. `DEMO_AUTO_STATUS` (этап 10) не трогаем.

## Готово, когда

Гость по uuid-ссылке видит смену таймлайна ≤25 с без перезагрузки (SQL-сдвиг `created → preparing → ready → in_delivery → delivered`); в Network видны 304/200; после `delivered` поллинг замолкает; отмена: кнопка → Dialog → баннер, повторный вход по ссылке показывает отмену, гонка-негатив («уже готовится») даёт toast-ошибку; карточка на главной показывает все активные заказы и исчезает по мере завершения; гость по ссылке не видит адрес/комментарий, владелец видит; `createOrder` пишет событие `created`, `cancelOrder` — отмену (верификация по БД); lint/tsc/build + docker build + prod compose (`up -d --build`, §5.28) зелёные; скриншоты — `.scratch/stage-4/screenshots/`; AGENTS обновлён (чекбоксы + §3), коммит.

## Вне скоупа

Платёжный UI и `paymentStatus`-бейдж (этап 9); ETA/слоты доставки; refund; отмена заведением из UI (этап 5); автоджоба статусов и SMS «готов» (этап 10); чтение `order_status_events` UI (этап 10); real-time через WS вместо поллинга (этап 6 — чат, не заказы); push в origin (по явной просьбе).
