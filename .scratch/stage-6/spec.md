# Спека: Этап 6 — Real-time чат поддержки (WebSockets)

Источник правды: AGENTS.md (§6 этап 6, §5.22 WS-механизм, §5.32-г NEXT_PUBLIC, §7 a11y). Гриллинг этапа 6 (2026-11-16/17, Q1–Q14) зафиксировал **вариант C — единый WS-релей записей**: и покупатель, и оператор шлют сообщения через WS-шлюз, который релеет их в служебный роут Next — секрет не живёт в браузере. Server Actions для чата отклонены (Q1: два пути записи = ручная стыковка optimistic-стейта и broadcast через два транспорта, честный режим отказа лучше половинчатого «отправил — а лента мертва»). Шлюз в dev поднимается на хосте, контейнер — только в prod-compose (Q11, отклонение от буквы старого плана). Панель виджета — Sheet (Q13). «Поиск в шапке» из старого описания этапа уже сделан коммитом переопределения 51f98e7 — из скоупа снят.

## Problem Statement

Поддержки нет ни у одной роли: гость с вопросом «есть ли шаурма без острого?» и клиент с проблемой заказа могут только уйти. Персонал (admin/manager) видит только факты заказов, не диалог: спросить не о чем, ответить некуда. Для проекта это ещё и единственный этап, демонстрирующий WebSockets — фичу, которой в монолите без отдельного бэкенда взять негде (Route Handlers WS не держат, §5.22).

## Solution

Плавающая кнопка чата на любой странице витрины (панель — Sheet справа): гость и клиент пишут в один тред со своей идентичностью (сессия или httpOnly-кука `chat_token`), переписка живёт в БД и переживает перезагрузку, ответ оператора прилетает в открытый чат без перезагрузки. У персонала — операторская `/admin/chats`: табы на каждый тред (телефон клиента или «unknown» у гостя), новые треды появляются табами сами, непрочитанные считаются, ответ уходит из таба. Транспорт — отдельный WS-шлюз (workspace-пакет на `ws` + Postgres LISTEN/NOTIFY), все записи — единым релеем через шлюз с живой серверной валидацией каждого сообщения.

## User Stories

1. Как гость-покупатель, я хочу открыть чат с поддержкой одной кнопкой с любой страницы витрины, чтобы задать вопрос без регистрации.
2. Как гость, я хочу получить ответ оператора прямо в открытый чат без перезагрузки страницы, чтобы диалог был живым.
3. Как гость, я хочу, чтобы моя переписка пережила перезагрузку страницы и повторное открытие чата, чтобы не терять контекст.
4. Как клиент (залогиненный), я хочу, чтобы мой гостевой тред стал тредом аккаунта после входа, чтобы история поддержки следовала за аккаунтом.
5. Как клиент или гость, я хочу видеть бейдж непрочитанных на кнопке чата, пока она закрыта, чтобы не пропустить ответ.
6. Как покупатель, я хочу видеть «Нет соединения» и неактивный инпут, когда чат-транспорт недоступен, чтобы понимать, почему сообщение не уходит.
7. Как оператор, я хочу видеть таб каждого треда с телефоном клиента (или «unknown» для гостя), чтобы понимать, с кем говорю.
8. Как оператор, я хочу, чтобы новый тред появлялся табом сам, без перезагрузки операторской, чтобы не пропускать обращений.
9. Как оператор, я хочу видеть счётчик непрочитанных на табе и уметь отвечать прямо из таба, чтобы вести несколько диалогов параллельно.
10. Как оператор, я хочу, чтобы непрочитанные сбрасывались, когда я открыл таб и прочитал (или получил сообщение живьём в открытый таб), чтобы бейджи показывали только непрочитанное.
11. Как второй оператор, я хочу видеть те же треды одновременно без клейма и назначения, чтобы кто-то из нас ответил.
12. Как владелец системы, я хочу, чтобы WS-подключение без идентичности отклонялось, а каждое сообщение перевалидировалось живым срезом БД, чтобы чужие не слушали чужие треды и забаненный отсекался на следующем же сообщении.
13. Как покупатель, я хочу, чтобы пустое или слишком длинное сообщение не ушло с понятной ошибкой, а история обрезалась последними 50 сообщениями без мусора.
14. Как оператор, я хочу, чтобы треды без единого сообщения клиента не создавали табов, чтобы пустышки не спамили операторскую.

## Implementation Decisions (гриллинг Q1–Q14, 2026-11-16/17)

- **Q1 — вариант C, единый WS-релей записей**: виджет и операторская шлют `{type:"send"}` по WS → шлюз релеет в служебный роут (`x-internal-secret`, секрет только на сервере) → Next живо перевалидирует identity по БД → INSERT + pg_notify в одной транзакции → NOTIFY-фанаут шлюзом в комнаты. Отправитель рендерит из эха: optimistic-строка с `tempId`, `ack` подтверждает, `error` тостит, `message`-echo дедуплицируется по id. Альтернатива B (Server Actions для записей) отклонена: гонка ответа action'а с WS-broadcast требует ручной стыковки двух транспортов; у C отказ целостный («нет соединения» = нельзя ни писать, ни читать), у B — половинчатый. HTTP-фолбэка у записи нет: WS упал → инпут дизейблится, reconnect с backoff + re-init.
- **Q2/Q10 — модель данных**: один постоянный тред на идентичность (без тредов-на-заказ); `chat_threads` — uuid pk, `user_id` text FK cascade nullable + unique, `guest_token` uuid nullable + unique, два `*_last_read_at`; `chat_messages` — bigserial pk (порядок = id, uuid не нужен — не в URL), thread_id cascade, `direction` text по константе `CHAT_DIRECTIONS` (pgEnum в проекте не используется — конвенция schema.ts), `sender_id` text FK set null, `text` 1..2000 после trim (zod-схемой, колонка без CHECK). Гостевой тред **усыновляется** при логине (UPDATE user_id) — только если у юзера ещё нет своего треда; потоки сообщений не мержатся, осиротевший гостевой тред принят. Кука `chat_token` — httpOnly, sameSite lax, path /, 30 дней (прецедент `cart_id`), выдаётся роутом init.
- **Q3 — бейдж непрочитанных при закрытом виджете**: WS при закрытом виджете нет («только по клику»), push невозможен → Server Action `getChatUnread` поллит 30 с; стартует только после первого открытия чата (флаг в localStorage — не-пользователи чата не поллят); `document.hidden` пропускает тик (паттерн OrderTracker). RSC-слот на навигации отклонён (не живой), постоянный WS — противоречит плану.
- **Q4 — объёмы**: текст 1..2000 символов после trim; init возвращает последние 50 сообщений («загрузить ещё» нет); лента оператора — 50 последних тредов по времени последнего сообщения, без пагинации; rate limiting нет (§9 роадмап). Кап 2000 гарантирует NOTIFY-payload < 8 КБ (лимит Postgres).
- **Q5 — прочтения**: `customer_last_read_at` = now при открытии виджета (в init), `operator_last_read_at` = now при открытии таба (WS `read` через шлюз → internal → UPDATE, без NOTIFY). Если сообщение пришло живьём в открытый виджет/таб — read уходит сразу (показано = прочитано). UI «прочитано»/typing нет ни у кого.
- **Q6/Q14 — операторская**: табы = до 50 тредов по последнему сообщению; треды без customer-сообщений не показываются (init-пустышки не создают табов — и отдельное «тред создан»-событие не нужно: таб появляется по первому message-NOTIFY); заголовок — телефон из JOIN или «unknown» (телефон кладётся в NOTIFY-payload при вставке); непрочитанные на табе = customer-сообщения после `operator_last_read_at`, пересчёт по каждому NOTIFY; закрытие таба — только UI; все операторы видят все треды, клейм/назначение нет. История таба — Server Action с гардами (админ+не забанен) — internal-роут браузеру недоступен. Страница рядом с заказами (admin+manager, вне admin-only зоны), пункт «Чаты» в наве.
- **Q7/Q11/Q12 — шлюз и инфраструктура**: workspace-пакет `ws-gateway` (поле `packages:` в pnpm-workspace.yaml — сейчас его нет; `ws` в проекте не установлен), TS→tsc, deps `ws`+`postgres`+zod; свой zod-env fail-fast (DATABASE_URL с фолбэком 5560, NEXT_INTERNAL_URL, PORT=3001, INTERNAL_API_SECRET). Upgrade-аутентификация: cookies пересылаются в get-session (куки не изолируются по порту) → оператор; иначе кука `chat_token`; иначе отказ + Origin-проверка. Комнаты в памяти: треды + `operators`; subscribe валидируется через internal один раз на соединение. ping/pong 30 с. **Dev — шлюз на хосте** (`pnpm dev:gateway`, node --watch + tsx-лоадер, ноль новых зависимостей; dev-compose остаётся инфраструктурным — контейнеризация шлюза в dev требовала бы пересборки на каждую правку, §5.28), **prod — multi-stage Dockerfile шлюза + сервис в prod-compose** (порт 3001 наружу). `NEXT_PUBLIC_WS_URL` — первый `NEXT_PUBLIC_*` в проекте: инлайнится на build → ARG в Dockerfile (дефолт `ws://localhost:3001`) + `build.args` в prod-compose; фолбэк-переменной для клиентского кода не существует (§5.32-г).
- **Q9 — протокол и internal-роут**: словарь WS: клиент→шлюз `subscribe{threadId}` / `subscribe-operators` / `send{threadId,text,tempId}` / `read{threadId}`; шлюз→клиенту `ack{tempId,message}` / `error{tempId?,code}` (validation|forbidden|banned|unavailable) / `message{threadId,phone,message}`. Internal-роут — один POST с discriminated union `{action:'send'|'read'|'join', identity, threadId, text?}`; identity `{customer,userId} | {guest,token} | {operator,userId,role}`; каждый send перевалидируется живым срезом БД (владение тредом; роль+`banned_at`+`deleted_at` для оператора — гвард-стиль этапа 5; забаненный отсекается на следующем же сообщении, не дожидаясь реконнекта). Секрет не задан → fail-fast; неверный → 403.
- **Q13 — форма виджета**: Sheet справа (компонент установлен с этапа 0) — фокус-ловушка, Esc, aria и мобильное поведение из Radix; плавающая панель над кнопкой отклонена (a11y руками, тесно на мобильном).
- **Q8/Q14 — размещение и раскладка**: виджет только в лейауте витрины (не на auth-страницах, не в /admin — операторы работают из операторской). Типы протокола — client-safe модуль на стороне Next + минимальный дубликат в шлюзе (шлюз — граничный сервис; workspace-экспорт типов ради ~30 строк оверинжиниринг; выделение третьего пакета — при росте). Root tsconfig исключает шлюз (другой moduleResolution), pre-commit проверяет `tsc` дважды. Biome покрывает пакет по умолчанию.
- **Кеш**: чат — динамика без 'use cache' (лента, треды, unread); операторская — connection()+Suspense по граблю админ-страниц §5.33; NOTIFY живёт мимо кеша Next (шлюз — не Next-процесс).
- **Механизм-константа**: всё выше согласовано с §5.22 (механизм WS в этом репо) — там же итоговое решение.

## Швы и приёмка (seams)

Высший шов — браузерная приёмка (рецепт `docs/agents/browser-testing.md`, читать до первой приёмки в сессии): гость пишет → у оператора появился таб → ответ виден гостю без перезагрузки (проверка по `performance.timeOrigin` — прецедент этапа 4). Ниже — два HTTP-шва, доступных curl: init (идентичность/кука/история) и internal (секрет/валидация/INSERT+NOTIFY); WS-upgrade без идентичности проверяется коннектом без кук. Состояние БД верифицируется SQL (строки messages, `*_last_read_at`, усиновление). Режим WS-down — остановкой шлюза. Приор-арт: приёмка этапа 4 (curl-ETag + web-gui-tester + SQL-верификация).

## Готово, когда

Гость пишет в виджет и получает ответ оператора без перезагрузки; у оператора таб появляется сам (телефон или «unknown»); история чата переживает перезагрузку; WS-upgrade без идентичности отклонён; WS-down дизейблит инпут и восстанавливается после рестарта шлюза; усиновление гостевого треда видно в БД и в заголовке таба; непрочитанные: бейдж закрытого виджета ≤30 с, бейджи табов по NOTIFY; lint/tsc×2/build зелёные; docker build + prod compose (`up -d --build`, §5.28) + возврат dev (§5.26); скриншоты — `.scratch/stage-6/screenshots/`; AGENTS обновлён (чекбоксы + §3), коммит.

## Вне скоупа

Typing-индикатор; UI «прочитано»; вложения/картинки; редактирование и удаление сообщений; rate limiting (§9); клейм/назначение операторов и распределение по тредам; звуки/пуши; TTL и архивация тредов; пагинация старых сообщений («загрузить ещё»); wss/TLS/домен (§9, Caddy); поиск в шапке (уже сделан в 51f98e7); e2e-тесты; push в origin (по явной просьбе).
