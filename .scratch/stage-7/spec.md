## Подготовка

1. **Нормализация стека** (сейчас гибрид: prod-app/gateway + dev-контейнеры одновременно): `docker compose -f docker-compose.prod.yml down` → `docker compose -f docker-compose.dev.yml up -d` (§5.26).
2. **Mailpit для prod-сессии**: сервис mailpit есть только в dev-компоузе; письма регистрации+/email нужны при поднятом prod-app. Поднять точечно: `docker compose -f docker-compose.dev.yml up -d mailpit` (общий проект/сеть — prod-app достучается по имени сервиса `mailpit`; проверить `SMTP_HOST` в env prod-app, иначе код уйдёт в консоль — тогда читать логи контейнера app).
3. `pnpm db:seed` (БД проверена 2026-11-17: все 4 акции живы, окно до 2026-12-16; reseed — гарантия идемпотентности).
4. **Подсадная корзина** для аудита `/checkout` (пока доступен postgres :5560): INSERT `carts` (uuid известный, `user_id null`) + `cart_items` (товары из сидера) — uuid запомнить, скрипт lighthouse поставит httpOnly-куку `cart_id` через CDP `page.setCookie`.
5. Сборка: `pnpm lint` → `npx tsc --noEmit` + `npx tsc -p ws-gateway/tsconfig.json --noEmit` (§5.27) → `pnpm build` → `docker build .` → `docker compose -f docker-compose.prod.yml up -d --build` (§5.28 — флаг обязателен).
6. Smoke prod: `GET /` → 200, `GET /api/promotions` → 200, ws-порт :3001 принимает upgrade (прецедент этапа 6).

**БД-верификации при поднятом prod** — только через `docker exec` в postgres-контейнер активного стека (`food-postgres` в dev; в prod имя compose-вида, искать через `docker ps`): `psql -U postgres -d food_delivery`. Хостовый psql на :5560 при prod-стеке падает (§5.28).

**Браузерная приёмка** — по рецепту `docs/agents/browser-testing.md` (§5.25, §5.34): стабильный rect → scrollTo instant → click; после мягких навигаций верификация скриншотом + БД/curl, не только evaluate; запутавшаяся вкладка — свежая вкладка. Каждый тест-пойнт: скриншот в `.scratch/stage-7/screenshots/` + опорная точка вне браузера.

**Демо-данные**: admin `+7 999 000-00-01`, manager `+7 999 000-00-02`, клиент `+7 999 000-00-03`; SMS-код всегда `1111`; Mailpit UI :8025, HTTP API `GET http://localhost:8025/api/v1/messages` (код письма — из JSON). IAB — одна куковая банка: гость и админ — последовательно; исключение — чат (см. Часть B, шаг 12: `chat_token` ≠ session-куки, два таба могут сосуществовать).

## Часть B — happy path (сквозной сценарий)

1. **Гость, главная**: «Акции недели», sticky-навигация по категориям (якорный скролл + scrollspy), секции меню рендерятся.
2. Модалка сета «Шаурма для двоих» (клик по карточке; `?product=<id>` в URL) → «В корзину». Бейдж Σqty обновился.
3. Добавить шаурму «Классическая».
4. **/cart**: применить SHAWARMA20 кнопкой из блока акций → скидка −20% **только от шаурмы** (тоталы верны, сверить с расчётом `calcDiscount`), подсказка доставки пересчитана.
5. Убрать шаурму → активное промо показывает причину «В корзине нет товаров из акции» и исключено из тоталов (фикс C1).
6. Вернуть шаурму → **/checkout** (tabs, inline-валидация RHF: пустые поля → aria-invalid) → создать заказ → redirect на `/orders/<uuid>`.
7. **БД**: строка orders (uuid, `discount_amount`, `delivery_fee`, снапшот items), строка `order_status_events` (`created`), корзина очищена.
8. **Гость на `/admin`** → redirect `/login` (proxy).
9. **Таб B, login admin** (телефон + OTP 1111) → `/admin/orders` → смена статуса `created → preparing` (inline select).
10. **Таб A: трекинг обновился ≤ 25 с без перезагрузки** — `performance.timeOrigin` неизменен, бейдж/поллинг сработали; curl-пруф: `GET /api/orders/<uuid>` — 200 после смены, 304 с `If-None-Match` на неизменном.
11. **Админка: создание** — новая акция (форма RHF, рубли→копейки) → `GET /api/promotions` обновился мгновенно (`updateTag('promos')`, §5.29); новый сет с составом (useFieldArray) → виден на витрине. Затем **оба деактивировать** (Q10a) — деактивация тоже проверена (акция исчезла из витрины/API).
12. **Чат**: таб A (гость, `chat_token` установлен) — открыть виджет, отправить сообщение; таб B (admin-сессия — куки разные с `chat_token`, сосуществуют) → `/admin/chats` → таб «unknown» → ответить. **Таб A: ответ виден живьём** (`timeOrigin` неизменен). Если два таба конфликтуют — фолбэк: последовательно с logout'ами (прецедент этапа 6, Т1–Т3); `chat_token` переживает logout админа.
13. curl-пруфы регрессии: 304 `GET /api/promotions` (ETag), 304 `GET /api/orders/<uuid>`.

- Скрипт `.scratch/stage-7/lighthouse/run.mjs`; зависимости `lighthouse` + `puppeteer-core` в root devDeps (Q8); Chrome системный (`C:/Program Files/Google/Chrome/Application/chrome.exe`). `node_modules` скрипта не коммитится (корневой .gitignore).

- Authed `/orders`: API-логин клиента `+7 999 000-00-03` (send-otp → verify `1111`; endpoints — по `src/lib/auth.ts`/`auth-client.ts`, прецедент curl-приёмки этапа 6).

- Форм-фактор desktop; отчёты: `.scratch/stage-7/lighthouse/<slug>-<theme>/{report.html,report.json}` — коммитятся.
- Порог: score ≥ 95 в каждом прогоне. Один прогон на пару; при 94–96 — один повтор, берётся лучший, отклонение документируется.
- Найденное < 95 → починка (Часть «Политика исправлений»), перегон пары страница×тема.

## Часть E — клавиатурный проход + reduced-motion

`prefers-reduced-motion: reduce`: эмулировать (DevTools-протокол через puppeteer `emulateMediaFeatures` либо флаг запускаемого Chrome) → модалки/тосты/скролл без анимаций, интерактив работает.
